# LiveTalking Studio — Linux

В интерфейсе одна личность называется **Persona**, несколько — **Personae**. Persona задаёт характер и память; аватар и голос выбираются отдельно.

Electron-интерфейс для локального LiveTalking. Интерфейс LiveTalking Studio отображается на английском; названия кнопок и состояний ниже приведены так, как они показаны в приложении. Приложение проверяет окружение, запускает Qwen ASR и выбранный Qwen/OmniVoice TTS, LiveTalking и сервис Persona, показывает аватара по WebRTC, озвучивает ответы, распознаёт микрофон, прерывает речь и сохраняет MP4. Persona ведёт постоянные разговоры и память в PostgreSQL.

## Запуск

Нужны Linux с графической сессией и Node.js 22 или новее:

```bash
cd LiveTalking/desktop
npm ci
npm start
```

Если npm запретил установочные скрипты зависимостей и Electron сообщает, что не установлен, один раз выполните:

```bash
node node_modules/electron/install.js
```

Приложение само находит родительский checkout LiveTalking. Для установленного приложения поиск рассчитан на папку `LiveTalking` рядом с исполняемым файлом; для AppImage используется расположение самого AppImage, а не временный mount. Выбор каталога вручную нужен только при другой структуре папок.

## Первый запуск

Мастер предлагает `.venv/bin/python` внутри LiveTalking, vLLM из соседнего `.venv` и vLLM-Omni из соседнего `.venv-omni`. Пути можно изменить. Python, CUDA и программные зависимости нужно установить заранее; недостающие веса Studio скачивает автоматически.

Пример существующей структуры:

```text
live/
├── LiveTalking/
│   ├── desktop/
│   ├── .venv/bin/python
│   ├── models/
│   └── data/avatars/
├── .venv/bin/vllm
├── .venv-omni/bin/vllm
├── .hf-cache-qwen/hub/
└── cloning/
    ├── voice_reference_name.wav
    └── voice_reference_name.txt
```

Для Qwen нужны `Qwen/Qwen3-ASR-0.6B` и `Qwen/Qwen3-TTS-12Hz-1.7B-Base`, vLLM и vLLM-Omni. Подготовьте отдельные окружения по [инструкции Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR#deployment-with-vllm) и [инструкции vLLM-Omni](https://docs.vllm.ai/projects/vllm-omni/en/latest/getting_started/quickstart/). При **Start** Studio скачивает недостающие веса MuseTalk/Wav2Lip/Ultralight и, в локальном режиме речи, Qwen ASR и выбранный Qwen TTS. Внешний режим не скачивает модели речи. Кеш выбирается в порядке `HF_HUB_CACHE`, `HF_HOME/hub`, существующая соседняя `.hf-cache-qwen/hub`, стандартный Hugging Face cache с учётом `XDG_CACHE_HOME`. Проверяется активная ревизия `refs/main`, конфигурации, токенизаторы, веса и все части разделённых весов.

Загрузка показывает название модели, общий прогресс и объём. **Stop** отменяет загрузку; повторное **Start** использует уже готовые файлы и докачивает текущий. Полученные байты сохраняются в `.studio-model-<id>.part` рядом с моделью при отмене, обрыве сети и закрытии приложения. Сохранённая часть привязана к источнику, закреплённой ревизии, размеру и контрольной сумме; прогресс при повторе учитывает эти байты. Если сервер не поддерживает продолжение, загрузчик начинает файл заново. Повреждённые части с неверной итоговой контрольной суммой удаляются.

Каждый новый файл проверяется целиком по размеру и контрольной сумме и только затем становится доступным модели; `.part` никогда не считается готовой моделью. Докачивание требует места для оставшихся байтов. Источники и ревизии Hugging Face закреплены в `server/desktop-model-catalog.json`; существующие непустые модели сохраняются. При запуске моделей Studio включает offline-режим Hugging Face, чтобы сервисы использовали подготовленный кеш. Для первого скачивания нужен интернет и свободное место: Qwen ASR/TTS вместе занимают примерно 6,5 ГБ.

### OmniVoice для клонирования голоса

В **Profile settings → Voice → Speech synthesis** можно выбрать **OmniVoice**. Он использует тот же WAV и точную расшифровку, что Qwen. Рекомендуется образец длительностью 3–10 секунд на языке будущей речи. Qwen остаётся выбором существующих профилей. При локальном режиме нужен отдельный Python с пакетом [OmniVoice из PyPI](https://pypi.org/project/omnivoice/) и веса [k2-fsa/OmniVoice](https://huggingface.co/k2-fsa/OmniVoice). Например, из каталога `live`:

```bash
uv venv --python 3.12 .venv-omnivoice
uv pip install --python .venv-omnivoice/bin/python 'omnivoice==0.2.1'
```

Убедитесь, что PyTorch в новом окружении видит CUDA. Studio по умолчанию ищет `../.venv-omnivoice/bin/python`; путь меняется в **Profile settings → Services → OmniVoice Python**. Веса OmniVoice занимают около 3,3 ГБ и загружаются при **Start** в тот же Hugging Face cache с проверкой размера и контрольной суммы. **Check setup** проверяет пакет, файлы модели и GPU. При локальном запуске Studio поднимает собственный OmniVoice HTTP-сервис после Qwen ASR, использует его в LiveTalking и останавливает вместе с профилем. Порт TTS по умолчанию остаётся `8091`; уже работающий Qwen TTS на этом порту нужно остановить перед сменой движка. В режиме **External servers** настройте TTS URL сервиса, совместимого с запросом `/v1/audio/speech` для PCM и клонирования по `ref_audio`/`ref_text`, и `/v1/models` с ID `k2-fsa/OmniVoice`.

При потоковом запросе Studio локальный сервер OmniVoice делит текст по предложениям, а длинное предложение — по знакам паузы, и отправляет PCM сразу после синтеза каждой части. Это потоковая выдача готовых фраз: PyPI 0.2.1 не выдаёт аудио внутри одной части. Короткая фраза без подходящего разделителя может прийти одним блоком. Qwen TTS отдаёт аудио по мере генерации внутри фразы. **Interrupt** прекращает выдачу в аватар; уже запущенный вызов OmniVoice может завершиться в фоне. Меньшая задержка первого звука у OmniVoice на длинном тексте достигается ценой повторных вызовов модели и более долгой полной генерации.

По умолчанию локальный OmniVoice использует 16 шагов декодирования для быстрого разговора. При запуске Studio он заранее кодирует выбранный WAV/TXT образец и прогревает генерацию фразой средней длины до объявления TTS готовым. Это убирает большую часть задержки первого запроса; выбор другого образца в уже запущенном сервисе снова потребует кодирования. Оригинальные 32 шага дают модели больше возможностей для качества, но примерно удваивают время первой части. Для сравнения на слух можно запустить Studio с `OMNIVOICE_NUM_STEP=32 npm start`; допустимы значения 4–64. Для сравнения моделей на одной машине запустите их по очереди с одним WAV, TXT и текстом, затем вызовите `scripts/compare_tts.py` для каждого URL. Скрипт сохраняет WAV и JSON с временем первого байта, полной задержкой, RTF и пиком видеопамяти. Передайте `--pid` для каждого GPU-процесса выбранного TTS, чтобы исключить ASR и аватар; без PID измеряется вся занятая видеопамять.

Готовый WAV и одноимённый TXT находятся автоматически в `LiveTalking/data/voices`, `LiveTalking/voices` или соседней папке `cloning`. В `cloning` используются файлы `voice_reference_*.wav`. Предлагается самый свежий образец; если их несколько, можно выбрать другой из списка. Расшифровка должна точно соответствовать записи. В этой версии профиль ссылается на исходный WAV: сохраняйте его на месте.

В блоке **Profile** нажмите **Choose avatar** для готового аватара или **Create avatar** для фото/видео. Модель определяется выбранной карточкой; вводить ID вручную не требуется. Для локального аватара нужен NVIDIA GPU даже при внешних ASR/TTS серверах. Внешний режим проверяет модели через `/v1/models` и не запускает vLLM.

Откройте **Profile settings → Services**, нажмите **Check setup**, исправьте указанные проблемы и сохраните настройки через **Save profile**, затем нажмите **Start**. При запуске профиль сохраняется автоматически. После первого успешного запуска он открывается и запускается сам, если включено «Start on launch». **Stop** завершает принадлежащие Studio процессы. При закрытии Studio с запущенными ею ASR/TTS появляется выбор **Keep running**, **Shut down** или **Cancel**. Оставленные серверы отображаются в списке Services после следующего запуска; кнопки **Stop ASR** и **Stop TTS** завершают их по отдельности. При остановке одного из речевых серверов активный профиль останавливается, второй сервер продолжает работать. Совместимые сервисы, которые уже работали до запуска приложения, остаются работать.

Во время запуска верхняя полоса показывает текущий этап, а строки сервисов — загрузку и прошедшее время; ожидающие этапы помечены «Queued». Это время ожидания, а не оценка оставшегося времени. На одном GPU локальная Qwen ASR загружается до Qwen TTS: одновременная инициализация приводила к нехватке памяти для KV-кеша. LiveTalking запускается после готовности обеих моделей. Холодная загрузка моделей в GPU может занимать минуты. JIT-кеши FlashInfer для ASR и TTS разделены: после первой компиляции каждый сервис использует свой готовый модуль вместо пересборки при переключении между Python-окружениями. Если задан `FLASHINFER_WORKSPACE_BASE`, Studio создаёт в нём отдельные `livetalking-studio/asr` и `livetalking-studio/tts`. Подсказка под кнопкой проекции объясняет, почему подключение пока недоступно. При следующем запуске Studio может использовать уже работающие совместимые сервисы.

В **Startup log** строки `LT_TIMING` показывают время импорта Python, инициализации аватара, загрузки SoulX pipeline, подготовки изображения и готовности HTTP. Проверка готовности локальных ASR/TTS повторяется каждые 0,5 с, LiveTalking — каждые 0,2 с; эти интервалы добавляют небольшую задержку после фактической готовности сервиса.

Нижняя строка подсказывает следующий шаг: настроить и запустить профиль, включить превью или проекцию, затем начать разговор. В левой панели показаны выбранный голос и режим собеседника. **Change voice** и **Change brain** открывают соответствующую вкладку окна **Profile settings**; вкладка **Services** содержит Python, пути окружений, адреса серверов и результаты проверки. **Check setup**, **Save profile** и **Start** показывают индикатор во время работы; проверки Python и GPU выполняются без блокировки окна. **Save profile** сохраняет изменения и закрывает окно. Если изменились аватар, каталог LiveTalking, Python или порт, Studio сначала останавливает работающий профиль; запись MP4 перед этим нужно закончить. Другие сохранённые настройки работающего профиля применяются после его перезапуска. Крестик или Escape отменяет несохранённые правки; Tab переключает элементы, стрелки переключают вкладки.

Ширину панелей **Profile** и **Conversation** можно менять, перетаскивая вертикальные разделители рядом с областью аватара. Выбранные размеры сохраняются между запусками и подстраиваются под ширину окна. Для управления с клавиатуры выберите разделитель клавишей Tab и используйте стрелки влево/вправо; Shift увеличивает шаг.

## Создание и библиотека аватаров

**Create avatar** открывает выбор исходника, имени и модели. MuseTalk v15 поддерживает PNG/JPEG и видео MP4/MOV/MKV/AVI; Wav2Lip — видео этих форматов. Экспериментальные Ditto и SoulX FlashHead Lite поддерживают PNG/JPEG. Подготовленные Ultralight доступны для выбора. Для фото используйте хорошо видимое лицо; видео нормализуется до 25 кадров/с без звука. Дополнительные параметры кропа и маски MuseTalk находятся в раскрывающемся блоке.

Первого аватара можно создать до настройки голоса, ASR/TTS и «Персоны». **Check** проверяет выбранное Python-окружение, CUDA, локальные веса и место на диске. При **Create** недостающие веса скачиваются автоматически: для MuseTalk — VAE, UNet v15, face parsing и детектор S3FD; для подготовки Wav2Lip — S3FD. Qwen при создании аватара не скачивается. Детектор ищется в `avatars/<model>/…/detection/sfd/s3fd.pth` или Torch Hub `checkpoints/s3fd-619a316812.pth`. Этап «Downloading models» показывает прогресс; **Cancel** останавливает worker и сохраняет текущую часть модели для докачивания. **Retry** использует готовые модели и продолжает прерванный файл. Python/CUDA и программные зависимости устанавливаются отдельно.

Подготовка показывает этап и прогресс. Закрытие диалога, в том числе Escape, оставляет её работать; кнопка **Show progress** возвращает к текущей задаче. **Cancel** завершает её собственный процесс. После ошибки/прерывания **Retry** использует сохранённую копию исходника, если копирование успело завершиться. Закрытие Studio отменяет текущую задачу; после аварийного выхода состояние восстанавливается как прерванное. Готовый результат публикуется только после проверки всех кадров.

При работающем профиле действия подписаны **Stop and create** или **Stop and select**. Сначала завершите запись MP4. После выбора или подготовки сервисы запускаются отдельной кнопкой **Start**. Смена аватара закрывает WebRTC и поток событий; «Persona» сохраняет незавершённый ответ, который доступен в истории того же разговора.

Библиотека показывает существующие и созданные аватары по имени и миниатюре. Есть поиск и переименование без изменения ID; одинаковые имена допустимы. Неполные/повреждённые каталоги показываются с причиной и недоступны для выбора. Выбор сохраняется в текущем профиле вместе с настройками голоса.

Миниатюры обрабатываются отдельным Python-процессом: слишком большие изображения (более 32 мегапикселей), повреждённое превью или недоступный интерпретатор оставляют карточку без картинки. Недоступный сохранённый checkout открывает настройки с ошибкой библиотеки, чтобы можно было выбрать другой путь. Эквивалентные пути, включая ссылку на checkout, используют одну библиотеку и состояние задачи.

Уже запущенный внешний LiveTalking должен сообщать модель и канонический каталог через `/api/desktop/health`; Studio проверяет их вместе с мозгом. При несовпадении выберите другой порт или самостоятельно перезапустите внешний сервис. Studio его не завершает. После обновления кода ранее запущенному серверу может потребоваться перезапуск для нового health-ответа.

Готовые аватары остаются в `LiveTalking/data/avatars/<id>`. Созданный аватар хранит `studio-avatar.json`, миниатюру и собственный исходник в `source/input.<extension>`: первоначальный файл после успеха можно удалить. Рабочие задания, копии для повтора и журнал находятся в `data/.studio-avatar-work/<jobId>` и не отображаются карточками. Голос настраивается отдельно; его исходный WAV пока нужно сохранять на месте.

### Ditto и SoulX FlashHead Lite

Эти модели заменяют генератор изображения MuseTalk для выбранного аватара. Qwen ASR/TTS, Persona, транспорт и запись используют прежние интерфейсы. Модели анимируют лицо по звуку, включая область глаз и щёк; отдельных контроллеров мышц или направления взгляда пока нет. До первой речи показывается исходный кадр; после речи SoulX сохраняет последний сгенерированный кадр. WebRTC и MP4 выдают 25 кадров/с, допускается одна активная сессия. SoulX генерирует 20 новых кадров/с, поэтому часть выходных кадров повторяется.

Создание карточки из фото не требует GPU или весов. Для запуска нужно один раз установить соответствующее окружение и модели. Скрипты выполняются из корня LiveTalking; нужны `uv`, Git, интернет и место под отдельное окружение/веса:

```bash
.venv/bin/python scripts/setup_ditto_engine.py
.venv/bin/python scripts/setup_soulx_engine.py --flash-attention
```

Установка закрепляет ревизии официальных репозиториев и весов, создаёт соседние `ditto-talkinghead/.venv` и `SoulX-FlashHead/.venv`, затем `models/<model>/runtime.json`. Ditto использует PyTorch из LiveTalking через `.pth`, дополнительные зависимости устанавливаются только в его окружение; основное окружение должно оставаться доступным. SoulX использует собственный PyTorch. Обычный **Start** проверяет установку и запускает отдельный worker; автоматический загрузчик Studio пока не устанавливает эти два движка. Автозагрузка Qwen продолжает работать.

На этой машине готовы карточки **Ditto** и **SoulX Lite** с копией текущей текстуры. Выберите карточку через **Select**, затем **Start** → **Enable preview**. Выбор движка сохраняется вместе с аватаром. Исходный MuseTalk остаётся доступен в библиотеке.

Исходные измерения RTX 3090 от 2026-10-04 на коротком WAV, без параллельно работающих Qwen (SoulX тогда использовал 25 кадров/с и четыре шага; после перехода на 20 кадров/с и два шага его скорость нужно измерять отдельно):

| Движок | Генерация | Память PyTorch, reserved | Режим |
| --- | --- | --- | --- |
| Ditto, PyTorch, 50 шагов | 7,9 кадра/с | 8290 МиБ, дополнительно ONNX | Подготовка реплики перед воспроизведением |
| SoulX FlashHead Lite, FlashAttention, без compile | 36,6 кадра/с; около 38 после первого блока | 5628 МиБ | Потоковый |

У Ditto `buffered_playback` по умолчанию включён: он сначала готовит реплику, затем воспроизводит согласованные звук и видео с нормальной скоростью. Длинная реплика дольше ждёт начала; временный буфер на диске ограничен 512 МиБ. Конец TTS-реплики либо пауза поступления аудио завершает буфер; **Interrupt** его сбрасывает. В runtime SoulX установлен `buffered_playback: false`. Если GPU занят и потоковый режим не успевает, можно включить буферизацию в `models/soulx/runtime.json` и перезапустить сервисы.

В SoulX поток TTS ждёт реальных сэмплов до полного блока либо сигнала конца: краткая пауза сети не добавляет искусственную тишину посреди фразы. Незаполненный хвост последнего блока не воспроизводится, между последовательными частями ответа сохраняется движение модели. Звук внутри фразы воспроизводится независимо от очереди сгенерированных кадров: при задержке видеоблока последний кадр повторяется, а опоздавшие кадры пропускаются. После метки конца следующая фраза снова ждёт свой первый видеокадр, чтобы её звук не обогнал липсинк. После начала речи в паузе остаётся кадр SoulX; первый переход от исходного фото занимает несколько кадров. SoulX Lite использует два шага генерации и 20 кадров/с. Для начала реплики он генерирует 8 кадров по 0,4 с аудио, затем возвращается к блокам по 24 кадра/1,2 с. Оба блока сохраняют единый motion context, а готовый кадр 512×512 масштабируется до размера текстуры фильтром Lanczos. Первый звук всё ещё ждёт соответствующего видеокадра; к этому ожиданию добавляются задержки LLM и выбранного TTS. Для Persona и SillyTavern первая часть длинного ответа отправляется в TTS уже после естественной паузы примерно от 35 символов, либо после границы слова около 72 символов, если паузы нет. Остальная разбивка ответа сохраняет прежние пороги.

На RTX 3090 контрольная 12-секундная синусоида с одновременной нагрузкой Qwen TTS раньше имела семь провалов звука по 0,22–0,30 с внутри сигнала (в сумме 1,7 с); после разделения аудио и видео в MP4 нет провалов от 40 мс. Проверены WebRTC, запись и повторное подключение. Это проверка непрерывности и тактовой частоты на тестовом сигнале; качество мимики при двух шагах и реальная речь требуют оценки на живом сеансе. Записи до и после лежат в `recordings/soulx-tts-contention-trial/` рядом с checkout.

Обе модели смягчают и деформируют исходную текстуру, поэтому исчезновение различий вокруг губ и точность физической проекции не гарантированы. Для сравнения сохранены ролики в соседних `recordings/ditto-trial/` и `recordings/soulx-trial/`. Физический показ Head in Jar требует отдельной проверки; приведённая скорость относится только к генератору аватара.

Совместный запуск с локальными Qwen ASR/TTS также проверен: короткий `Speak text` дал реальный звук, движущееся видео и MP4 у обоих движков. Стандартные параметры памяти сохранены (ASR 0,18, TTS deploy по умолчанию). Общее пиковое потребление GPU: SoulX 19503 МиБ, Ditto 23776 МиБ из 24576 МиБ — у Ditto запас небольшой. Холодный запуск SoulX вместе с речевыми моделями занял 114 с; первая озвучка с холодным TTS началась через 16,3 с. Ditto с уже загруженными Qwen начал озвучку через 18,2 с, включая подготовку видео. Это короткие проверки, не длительный нагрузочный прогон. Метрики и записи: `recordings/<engine>-trial/local-qwen-metrics.json` и `local-qwen-webrtc.mp4` рядом с checkout.

## Разговор

1. Дождитесь состояния «Running» и нажмите **Enable preview**.
2. Введите текст и выберите «Chat with LLM» или «Speak text». В режиме «Persona» все запросы `chat` к LiveTalking, включая внешние клиенты, проходят через него. В прямом режиме LLM использует настройки LiveTalking в `config.yaml` и `.env`. «Speak text» в обоих режимах отправляет текст прямо в TTS.
3. Для речи нажмите **Microphone**, произнесите фразу и нажмите **Stop**. Проверьте расшифровку и отправьте её. Начало захвата прерывает текущую речь аватара.
4. **Interrupt** останавливает озвучивание. **Record MP4** начинает запись; повторное нажатие завершает её и открывает диалог сохранения MP4. Перед отключением превью или остановкой профиля нужно завершить запись; во время смены разговора запись недоступна.

Редактирование текста остаётся доступным при ошибке микрофона. При потере WebRTC-сессии отправка и запись отключаются. Изменение Python, моделей, порта и TTS требует Stop/Start; параметры аватара и голоса используются при новом подключении.

Для разговора без кнопок подключите предпросмотр или проекцию и нажмите **Auto conversation**. Studio оставляет микрофон открытым, определяет фразу по голосу, показывает промежуточный текст **Hearing: …** во время речи и после примерно 0,9 секунды тишины отправляет итоговую расшифровку в режим «Chat with LLM» активного аватара. После ответа аватара слушание возобновляется. Под строкой состояния показывается уровень входящего звука: «waiting for signal» означает, что аудиоданные ещё не поступили; постоянно низкий уровень при речи подсказывает проверить усиление микрофона. Кнопка **Stop auto conversation**, Stop профиля или отключение аватара освобождают микрофон. Ручной режим **Microphone** тоже показывает промежуточный текст в строке состояния; итоговый текст появляется в поле сообщения после **Stop**.

Пока аватар отвечает, автодиалог обычно не распознаёт новую фразу: так звук TTS из колонок не запускает следующий запрос. В разделе **Options** рядом с **Auto conversation** флажок **Allow interruption** включает распознавание во время ответа. Уровень звука начинает захват, но озвучка прерывается после трёх распознанных слов в промежуточном тексте Qwen ASR либо после короткой команды остановки: «стоп», «хватит», «остановись», «прекрати», «помолчи», «подожди» и близких явных форм. Команда останавливает ответ без нового запроса в чат; случайное упоминание слова «стоп» внутри короткой фразы командой не считается. Промежуточный результат может прервать ответ только после минимальной длительности речи, поэтому короткий шум с ошибочным текстом не должен срабатывать. Другие фразы короче трёх слов во время ответа игнорируются, а в тишине по-прежнему принимаются. Студия посылает Qwen накопленное аудио не чаще раза в 0,75 с, начиная примерно с 0,9 с записи. Итоговая расшифровка после паузы всё ещё определяет, какая реплика уйдёт в чат. Для SenseVoice и старого сервера без промежуточных результатов перебивание ждёт итогового текста с тем же порогом. Используйте наушники или проверьте эхоподавление на месте показа: при громких колонках ASR может распознать голос самого аватара.

Ditto и SoulX при запуске готовят короткий цикл кадров по тихому аудио. Аватар показывает его без звука до первой реплики, между ответами и после перебивания; переходы между молчанием и речью сглаживаются. Подготовка добавляет один проход генерации к запуску LiveTalking, а не к каждой реплике. Внешний вид и дополнительное время на конкретном GPU проверьте в реальном сеансе.

## Проекция через Head in Jar

1. Подключите проектор как отдельный дисплей. В Head in Jar откройте проект с OBJ головы, выберите **Live video · WebRTC** и в **Connection access** укажите интерфейс своей локальной сети. Запустите сервер подключения. На Linux для поиска через mDNS должны работать Avahi и его daemon.
2. В Studio выберите аватар и разговор с Персоней, запустите профиль и в блоке **Head in Jar** откройте **Connection settings** и выберите найденный экземпляр. Нажмите **Done**, чтобы вернуться на главный экран. Studio подставит WHIP URL и очистит токен. Нажмите **Connect projection** и дождитесь статуса **Stream connected**. Поиск обновляется автоматически примерно раз в 15 секунд; Head in Jar на том же компьютере находится и без Avahi. По умолчанию клиенты выбранной подсети подключаются без токена. Если в Head in Jar включено **Require token**, Studio покажет это у найденного экземпляра: скопируйте Bearer token в Head in Jar и вставьте его в Studio в разделе **Advanced · token** перед подключением. Сам токен не публикуется через mDNS и не сохраняется в профиле. Для подключения на той же машине выберите **This computer** в Head in Jar; Studio найдёт его через локальную проверку даже без Avahi. Настройка **Require token** действует и для этого режима.
3. Проверьте живой кадр в Head in Jar, выберите проектор и нажмите **Start projection**. При смене разрешения дисплея проверьте физическую калибровку заново. Studio не включает проектор автоматически.
4. Говорите через микрофон Studio: после **Stop** проверьте распознанный текст и отправьте его. Чат, озвучивание текста, прерывание и запись направляются в проецируемый сеанс. Предпросмотр WebRTC Studio используется отдельно; перед переключением между ним и проекцией отключите текущее подключение.

При потере WHIP-потока Studio перестаёт отправлять в него реплики; выберите найденный Head in Jar повторно либо вставьте новый токен для ручного режима. **Stop** и закрытие Studio разрывают только WHIP-сеанс, запущенный этим окном. Сохранённый разговор Персоны остаётся доступен после переподключения. Head in Jar выводит звук полученного WebRTC-потока через выбранное системное аудиоустройство; перед показом проверьте акустику отдельно.

## Persona как мозг аватара

В **Profile settings → Brain → Avatar brain** выберите **Persona**. Приложение ищет checkout рядом с LiveTalking или в `~/persona` и предлагает его `.venv/bin/python`. Нужны подготовленное окружение Python 3.13 с зависимостями Persona, API-ключ Yandex AI Studio, folder ID и PostgreSQL с pgvector. Для локальной базы нужен работающий Docker Compose; приложение запускает только сервис `db` из `persona/compose.yaml`. Установка зависимостей описана в README самого Persona.

Параметры из `.env` LiveTalking и Persona подхватываются автоматически. Ключ и URL внешней базы также можно ввести в интерфейсе: они передаются сервису через окружение. При доступном Linux keyring сохраняются зашифрованно, иначе действуют до закрытия приложения. Интерфейс сообщает, какой способ доступен; секреты не попадают в профиль, аргументы запуска или журнал. Для внешней базы выберите соответствующий режим и задайте `PERSONA_DATABASE_URL`. Голосовая модель по умолчанию — Qwen3.6 35B; для сравнения можно задать в `.env` Persona `PERSONA_SPEECH_MODEL=aliceai-llm-flash` или `PERSONA_SPEECH_MODEL=deepseek-v4-flash`.

Если API уже запущен, приложение использует его. Для внешнего сервера выключите локальное управление и укажите URL. Сервер должен отвечать на `/health` и объявлять `speech_stream: 1` через `/api/v1/capabilities`; текущая ветка `main` проекта Persona поддерживает этот контракт. Сохранённые профили со старым режимом `batya` переводятся в `persona`, а путь к перенесённому checkout обновляется автоматически. Прежние `BATYA_DATABASE_URL` и `BATYA_SPEECH_MODEL` в `.env` остаются рабочими.

При **Start** сначала готовится «Persona» и база, затем серверы речи и LiveTalking. **Stop** завершает принадлежащие приложению процессы и контейнер базы. При закрытии аватар и Persona останавливаются; ASR/TTS следуют выбору в диалоге выхода. Уже работающие API и база остаются работать; том PostgreSQL сохраняется.

Перед WebRTC выберите сохранённый разговор или создайте новый. Его ID сохраняется в профиле; переподключение и перезапуск восстанавливают историю. Кнопка **New** и выбор другого разговора переключают «Персону» без отключения WebRTC или проекции. Текущая озвучка останавливается, а прежний ответ завершается и сохраняется в старом разговоре. Во время записи MP4 смена разговора недоступна. Внешний WebRTC-клиент может передать UUID как `persona_conversation_id` в `/offer`; без него разговор создаётся автоматически. Для смены разговора у действующего сеанса доступен `POST /api/brain/session` с `sessionid` и `conversation_id`. Каждый запрос `chat` может передать стабильный `request_id` для повторной доставки без второго запроса к модели.

Ответ появляется постепенно и сразу разбивается на короткие фразы для TTS. После поиска контекста «Persona» запускает ответ и проверку необходимости сохранить личный факт параллельно. Первые слова больше не ждут проверку памяти; перед окончательным `done` запись памяти завершается. Ответ выдаётся потоком без инструментов, поэтому служебный текст не попадает в речь. TTS работает параллельно с генерацией текста; короткий ответ может закончиться раньше появления первого звука из-за задержки синтеза. В журнале «Персоны» строки `persona_latency` показывают время поиска, первого текста и завершения.

**Interrupt** очищает текущую речь и запрещает дальнейшую озвучку прерванного ответа. «Persona» завершает и сохраняет его; следующий запрос в том же разговоре ждёт завершения предыдущего. При ошибке доступны сообщение и повтор с тем же ID. Кнопка **Memory & documents** открывает отдельное окно, где можно посмотреть память и явно загрузить текстовый документ. Загрузка книг и индексация автоматически не выполняются.

## SillyTavern как альтернатива Persona

Сохранённые профили выбираются в списке **Profile** в верхней панели Studio. Чтобы перейти с `Main` на `SillyTavern`, нажмите **Stop**, выберите `SillyTavern` и нажмите **Start**. Пока сервисы запущены, выбор профиля заблокирован; запись MP4 нужно сначала завершить. Если профиля ещё нет, в **Profile settings → Brain → Avatar brain** выберите **SillyTavern · characters and chats** и сохраните настройки текущего профиля.

Studio ищет checkout в `~/SillyTavern` и запускает его на `http://127.0.0.1:8001`, если он ещё не запущен. Запуск в Studio не открывает браузер; веб-интерфейс SillyTavern доступен по этому адресу после запуска сервиса. Для первого запуска установите зависимости командой `cd ~/SillyTavern && npm ci`. Нужен Node.js 22 или новее. Если Chat Completion в SillyTavern ещё не настроен, Studio один раз задаст Custom источник Yandex AI Studio: для этого нужны ключ и folder ID из `.env` LiveTalking/Persona или настроек профиля. Доступ к SillyTavern ограничен локальным адресом.

При первом запуске с персонажем по умолчанию Studio создаёт карточку **Виктор Петрович** из первых трёх абзацев промпта Persona. В панели **Conversation** список **SillyTavern character** показывает все карточки текущего пользователя SillyTavern; **Refresh characters** обновляет его. Выбранный персонаж сохраняется в профиле Studio. Переключать его можно и при подключённом WebRTC/WHIP: Studio создаёт для новой карточки отдельный разговор и меняет адресат действующего сеанса без перезапуска моделей. Во время записи MP4 и отправки реплики переключение заблокировано.

Разговоры сохраняются обычными чатами выбранной карточки SillyTavern. Studio использует локальные маршруты SillyTavern для карточек, чатов и потоковой генерации через выбранный источник Chat Completion; небольшой мост на `127.0.0.1:8002` связывает их с существующим потоком речи LiveTalking. При **Stop** завершаются только процессы SillyTavern и моста, которые запустила Studio.

В этом режиме история хранится в SillyTavern отдельно от Persona и отдельно для каждой карточки. Память Persona, документы и инструменты сохранения памяти не переносятся. Studio передаёт SillyTavern только выбранную карточку, ID беседы, ID запроса и новую реплику; потоковый `/api/characters/chat` применяет карточку, выбранные лорбуки и глобальный порядок промптов, а после завершения ответа сохраняет обе реплики. Потоковые части сразу уходят в озвучку. Расширения SillyTavern и сложные режимы активации World Info этим API пока не охвачены.

После первой настройки модель выбирается в SillyTavern; Studio больше не перезаписывает уже выбранный Chat Completion источник. Если Studio сама запускает SillyTavern, ключ передаётся его процессу через `SILLYTAVERN_CUSTOM_API_KEY`, а в настройках остаётся только ссылка `${ENV:SILLYTAVERN_CUSTOM_API_KEY}`. Эту переменную можно задать и в окружении Studio. Если Studio подключилась к уже работающему SillyTavern и источник ещё не настроен, ключ сохраняется в его хранилище секретов, а настройки содержат `${SECRET:CUSTOM}`. Ключ не записывается в профиль Studio или `settings.json` SillyTavern.

## Данные и диагностика

Профили находятся в Electron userData (обычно `~/.config/livetalking-desktop/profiles.json`). В профиль не записываются API-ключи. Повреждённый JSON сохраняется как `profiles.corrupt-*.json`, после чего мастер открывается с пустыми настройками.

Журнал запуска доступен в левой панели. Отдельные логи моделей остаются в `/tmp/livetalking-qwen-*`. Исходные записи сервера находятся в `LiveTalking/data/record`; диалог сохранения копирует выбранный MP4 в указанное место.

После запуска приложение продолжает проверять доступность LiveTalking и серверов речи. Ошибка отображается у соответствующего сервиса; после устранения причины можно повторить запуск. Повторные нажатия Stop используют одну процедуру остановки. Уже работающие внешние сервисы приложение не завершает.

## Проверки

```bash
npm test
npm run build
npm run smoke
npm run smoke:ui
```

Smoke-тест запускает локальный fixture и отдельные временные профили: настройка → Start → WebRTC session → текст → interrupt → Stop, автодиалог → ASR → автоматическая отправка в чат, подключение проекции → реплика в WHIP-сеанс → обрыв/повтор, а также «Persona» → потоковый ответ → прерывание → история после переподключения и перезапуска → ошибка и повтор → возврат в прямой режим. Проверяются также создание аватара до настройки голоса, прогресс при закрытом диалоге, миниатюра/выбор после перезапуска и удаления исходника, переименование/поиск, ошибка/повтор, отмена/закрытие и смена модели после записи во время ответа «Персоны». Модели и GPU ему не нужны. Скриншоты и журнал записываются в игнорируемый `test-results/`.

`npm run smoke:ui` проверяет изменение ширины обеих панелей, сохранение размеров, работу в узком окне, защиту записи при отключении превью, обновление списка разговоров во время ответа, повторное нажатие «New», отмену распознавания при смене разговора и сохранение нового черновика во время отправки. Использует временный профиль и fixture; скриншоты находятся в `test-results/ui-audit/`.

На текущей машине отдельно проверены холодный запуск моделей, реальное WebRTC-видео и аудио, echo, ответ LLM, прерывание, MP4 и WebAudio → Qwen ASR → озвучивание. Для проверки ASR использован виртуальный микрофон с русским WAV; физическое устройство нужно проверить своей фразой.

Интеграция Persona проверена с существующей локальной базой, настоящим API Yandex, Qwen TTS и WebRTC, включая сохранение разговора после перезапуска API и Electron. Тесты базы запускаются в отдельной временной PostgreSQL-базе; рабочая база сохраняется.
