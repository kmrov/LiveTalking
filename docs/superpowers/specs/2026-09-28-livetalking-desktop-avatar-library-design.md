# Создание и библиотека аватаров в LiveTalking Studio

Дата: 2026-09-28. Сценарий согласован в беседе; этот документ предназначен для проверки перед составлением плана реализации.

## Цель и согласованный сценарий

Пользователь создаёт аватара прямо в Electron: выбирает фото или видео, задаёт понятное имя, наблюдает подготовку и затем выбирает результат по имени и миниатюре. Созданные аватары, их исходники и названия сохраняются после закрытия Studio. Запоминать или вводить slug для обычной работы не требуется. Уже подготовленные аватары из выбранного checkout также доступны в библиотеке.

Создание первого аватара работает до настройки голоса, ASR, TTS и «Бати». Требуются совместимый checkout LiveTalking, его Python-окружение, NVIDIA GPU и локальные веса для подготовки выбранной модели. Studio проверяет зависимости и сообщает, чего не хватает; автоматически устанавливать пакеты и скачивать модели этот сценарий не должен.

В первой версии:

- MuseTalk v15 создаёт аватары из PNG/JPEG и видео MP4/MOV/MKV/AVI.
- Wav2Lip предлагается как дополнительный вариант для видео; для фото используется MuseTalk.
- Готовые Ultralight-аватары можно выбрать из библиотеки. Создание Ultralight требует отдельного checkpoint и остаётся за пределами этой задачи.
- Голос остаётся настройкой существующего профиля: WAV и точная расшифровка. Звуковая дорожка исходного видео не становится голосом автоматически.
- Для фотографии движение основывается на одном портрете; генерация новых движений головы в этот сценарий не входит. Видео даёт последовательность исходных движений.
- Переименование карточки входит в библиотеку. Удаление готовых аватаров, импорт ZIP, обучение моделей, монтаж видео, библиотека голосов и экспорт пакетов не входят в первую версию.

## Текущее состояние и выбранная архитектура

Сейчас `desktop/renderer/studio.html` содержит текстовое поле `avatar-id`. Профиль хранит пару `liveTalking.model` / `liveTalking.avatarId`. Проверка запуска требует существующего `data/avatars/<avatarId>`, а `app.py` загружает выбранного аватара при старте. Поэтому `/api/avatar/task` на запущенном LiveTalking не решает создание первого аватара.

В репозитории уже существуют `avatars/musetalk/genavatar.py` и `avatars/wav2lip/genavatar.py` с функцией `generate_avatar` и callback прогресса. Их использует серверный `TaskManager`, но его задачи живут только в памяти, нет библиотеки с названиями и нет остановки выполняющейся задачи.

Выбран отдельный Python-процесс подготовки под управлением Electron main. Он вызывает существующие генераторы через небольшой desktop-адаптер. Библиотека читается локально через main и узкий preload API. Создание не зависит от HTTP-сервера, голосового профиля и базы данных. Существующий HTTP API и его потребители продолжают работать; менять его контракт ради Studio не требуется.

Альтернатива — расширить HTTP API библиотекой и постоянными задачами — потребовала бы специального запуска сервера без аватара и отдельного управления его GPU-состоянием. Для локального приложения отдельный worker проще связывает подготовку с закрытием окна, отменой и хранением файлов.

## Пользовательский интерфейс

В левой панели появляется блок «Аватары» с выбранным именем и миниатюрой, кнопками «Выбрать» и «Создать аватара». Текстовое поле slug заменяется библиотекой; технический ID доступен в сведениях о карточке. Основной экран разговора сохраняет существующую структуру.

«Выбрать» открывает доступный с клавиатуры диалог библиотеки. Карточка содержит миниатюру, имя, модель и состояние. Есть поиск по имени и техническому ID, кнопка обновления и пустое состояние с действием «Создать аватара». Некорректные и неполные каталоги имеют описание проблемы и недоступны для выбора. Существующему аватару без собственного имени сначала присваивается имя каталога; пользователь может его переименовать.

«Создать аватара» открывает форму:

1. Выбор локального файла через системный диалог и превью фото или первого кадра видео.
2. Название, по умолчанию взятое из имени файла, с возможностью редактирования.
3. MuseTalk по умолчанию; выбор Wav2Lip доступен только для видео. Подсказка рекомендует хорошо видимое лицо одного человека.
4. Свернутые дополнительные настройки: MuseTalk `bbox_shift` — целое от −50 до 50, `extra_margin` — целое от 0 до 100, `parsing_mode` — `jaw`/`neck`/`raw`; Wav2Lip `pads` — четыре целых от 0 до 200, `nosmooth` — boolean, `face_det_batch_size` — целое от 1 до 128. Значения по умолчанию соответствуют используемым генераторам. Ограничения валидируются в main и worker; дополнительно проверяется допустимость итогового кропа для конкретного кадра. Размер лица Wav2Lip определяется рабочей конфигурацией модели, а не задаётся произвольным числом пользователем.
5. Результаты проверки именно подготовки: файл, Python, CUDA, веса и свободное место для записи. Отсутствие голоса и Qwen не блокирует эту форму.
6. «Создать», индикатор этапа и прогресса, «Отменить», а при неудаче — причина и «Повторить».

Подготовка работает в фоне, пока окно открыто. Закрытие диалога не отменяет процесс: состояние остаётся в блоке «Аватары». Одновременно выполняется одна задача в Studio; вторая кнопка создания недоступна с объяснением. Очередь задач не вводится.

После успеха карточка сразу появляется в библиотеке с действием «Выбрать». Создание само по себе не меняет текущего аватара и не запускает сервисы. Переименование карточки не меняет ID и ссылки существующих профилей.

Тексты состояния и ошибок на русском. Изменение этапа объявляется через `role="status"`, ошибки через `role="alert"`; индикатор имеет доступное имя и числовое значение. Диалоги удерживают фокус и возвращают его к вызвавшей кнопке. Escape закрывает диалог, а отмена задачи выполняется отдельным действием.

## Хранение и обнаружение

Готовый результат хранится в выбранном checkout: `<root>/data/avatars/<generatedId>/`. Это сохраняет совместимость с текущими загрузчиками и CLI. Библиотека относится к выбранному каноническому пути checkout; смена root обновляет список. Профиль по-прежнему хранит `model` и `avatarId`, без абсолютного пути к исходному изображению.

Для новых аватаров main создаёт ID `studio_<UUID без дефисов>`. ID не зависит от пользовательского названия, поэтому кириллица, пробелы и одинаковые имена не вызывают коллизий. Каталоги с таким ID никогда не перезаписываются; при коллизии выбирается новый ID.

Внутри готового каталога:

- стандартные артефакты выбранного генератора;
- `studio-avatar.json` — версия схемы, ID, имя, модель, дата создания, число кадров, относительное имя исходника и параметры подготовки;
- `source/input.<разрешённое расширение>` — собственная копия исходника;
- `thumbnail.jpg` — миниатюра первого готового кадра.

Имя — непустая строка до 120 символов без NUL и управляющих символов. Метаданные не содержат секретов или произвольных путей. Файлы JSON записываются через временный файл и rename в том же каталоге. Ошибка записи не должна превращаться в сообщение об успешном сохранении.

Незавершённая работа размещается вне библиотеки: `<root>/data/.studio-avatar-work/<jobId>/`. Здесь находятся журнал, состояние задачи, скопированный источник, нормализованный вход и `output/<generatedId>/`. Готовый каталог появляется в `data/avatars` одним rename только после валидации, сохранения источника, миниатюры и метаданных. Ошибка или отмена не оставляет выбираемую карточку с неполными файлами. Повтор создаёт новую задачу и новый ID, используя сохранённую копию источника.

Журнал задачи ограничен по размеру; пользователь видит путь и последние строки при ошибке. Незавершённые/неудачные задачи и их источники сохраняются для диагностики и повтора. Успешная задача удаляет промежуточные нормализованные файлы, оставляя краткую запись о результате и журнал. Удаление готовых данных при очистке рабочих файлов запрещено.

При сканировании не выполняются Python-импорты и не десериализуются pickle/PT-файлы. Проверяется наличие непустых обязательных файлов и последовательностей изображений:

| Модель | Признаки готового каталога |
| --- | --- |
| MuseTalk | `full_imgs`, `mask`, `coords.pkl`, `mask_coords.pkl`, `latents.pt` |
| Wav2Lip | `full_imgs`, `face_imgs`, `coords.pkl`, без признаков MuseTalk/Ultralight |
| Ultralight | `full_imgs`, `face_imgs`, `coords.pkl`, `ultralight.pth` |

У кадров должны быть числовые имена и допустимые расширения; для соответствующих изображений/масок проверяются согласованные числовые индексы и количество, без требования одинакового расширения. Для новых результатов worker дополнительно проверяет согласованность координат, латентов и кадров до публикации. Неизвестный, противоречивый или повреждённый набор файлов отображается как недоступный с конкретной причиной. Читаемые старые данные не переписываются при сканировании.

`studio-avatar.json` уточняет модель, но не отменяет проверку артефактов. Для старого готового каталога переименование создаёт только этот manifest, с происхождением `existing`; исходник, дата его подготовки и параметры не выдумываются. Миниатюра старого аватара берётся из первого числового кадра через ограниченное чтение main. Отсутствие миниатюры не делает иначе готового аватара неисправным.

Символические ссылки на каталоги и артефакты за пределами канонического `data/avatars` не используются. Работа с рабочими каталогами также ограничена собственным каноническим корнем. Повреждённые метаданные получают видимое предупреждение; их нельзя молча затереть при переименовании.

## Worker и подготовка медиа

Новый скрипт `scripts/prepare_desktop_avatar.py` принимает путь к проверенному JSON-заданию, созданному main. Python запускается из выбранного профиля, с cwd checkout, без shell и с отдельной группой процессов. Задание содержит только версионированные поля, созданные main; worker повторно проверяет модель, допустимые параметры и границы путей.

Worker:

1. Проверяет доступность выбранного генератора, NVIDIA CUDA и всех весов подготовки, включая детектор лица и face parsing. Используются только локальные веса; автоматическое скачивание детектором должно быть предотвращено до его инициализации. Проверка подготовки отличается от проверки весов, необходимых только во время разговора.
2. Копирует исходник в рабочий каталог до запуска дорогих операций. После копирования удаление исходного пользовательского файла не ломает задачу или готовый аватар.
3. Декодирует и нормализует вход. Фото сохраняется как PNG `00000000.png` с корректной ориентацией, без дублирования исходного файла в `full_imgs`. Видео нормализуется через локальный FFmpeg в 25 fps без звука, с учётом ориентации, поскольку LiveTalking воспроизводит кадры с этой частотой. FFmpeg проверяется для видео; фотографии не требуют его наличия.
4. Вызывает существующую `generate_avatar` с рабочим `save_path`, передавая callback прогресса. Проблемы импортов адаптируются точечно, без реорганизации всех модулей генерации.
5. Проверяет результат, создаёт миниатюру и возвращает завершение. Main записывает manifest и публикует каталог после проверки результата.

Если лицо не найдено или координаты/кроп некорректны, подготовка завершается понятной ошибкой. Нулевое число кадров, неподдерживаемый кодек и недекодируемое фото также являются ошибками. Генератор не должен молча объявлять успех с пустыми координатами или использовать весь кадр вместо отсутствующего лица. Нужные изменения обработки ошибок затрагивают только используемые генераторы и сохраняют их CLI/API-сигнатуры.

Подготовка Wav2Lip использует действующее разрешение сервера и передаёт его в `img_size`. Проверка кода при составлении плана уточнила: сейчас `app.py` прогревает модель в 256×256, а `modelres` из конфигурации не определяет размер используемых кадров. Поэтому для текущего серверного контракта подготовка использует 256×256. Готовый результат не должен зависеть от неиспользуемого значения конфигурации, значения по умолчанию в HTTP-роуте или другого размера из старого примера.

Структурированные строки stdout имеют отдельный префикс `LT_AVATAR ` и JSON: версия протокола, `jobId`, состояние, этап, процент и сообщение. Прочие stdout/stderr сохраняются как журнал. Этапы: `checking`, `copying`, `normalizing`, `generating`, `validating`, `publishing`. Worker перед завершением сообщает `prepared`, означающее готовность рабочего результата; состояния `publishing` и `completed` задаёт только main. Проценты генератора отображаются как прогресс этапа подготовки; интерфейс не объявляет 100% задачи до публикации готового каталога. Main ограничивает размер строк и сообщений и игнорирует события чужого jobId или неизвестной версии.

Завершение worker с кодом 0 без подтверждённого валидного результата считается ошибкой. Exit/error и запоздавший callback обрабатываются идемпотентно; терминальное состояние задачи не меняется повторно. После входа в `publishing` отмена недоступна на короткое время атомарного завершения. Успешно опубликованный результат не удаляется из-за позднего запроса отмены.

## Жизненный цикл и взаимодействие с сервисами

Состояния задачи: `checking` → `running` → `publishing` → `completed`; до публикации возможны `failed`, `cancelling` → `cancelled`. При восстановлении существует терминальное состояние `interrupted`. Проверка и копирование входят в cancellable-фазу. Ошибка публикации переводит задачу в `failed` и сохраняет подготовленный рабочий результат для диагностики.

Main сериализует команды запуска профиля, выбора аватара и начала/отмены подготовки. Пока задача активна, запуск профиля и смена root/Python в интерфейсе недоступны; повторная IPC-команда также отклоняется. Переименование и просмотр библиотеки доступны.

Если профиль запущен, создание требует явного действия «Остановить и создать». Перед остановкой UI запрещает продолжение при записи MP4 и предлагает закончить запись; активный захват микрофона завершается. Затем закрываются клиентские WebRTC/SSE/ASR ресурсы и вызывается существующий `stopProfile`. Это действие может остановить все сервисы, которыми владеет профиль, включая управляемую «Батю». Используется существующая политика владения: подключённые сторонние процессы/контейнеры и том PostgreSQL сохраняются. Одного отключения WebRTC недостаточно для освобождения GPU от моделей сервера.

После остановки профиль автоматически не перезапускается ни при успехе, ни при ошибке, ни при отмене подготовки. Пользователь выбирает готовую карточку и нажимает привычное «Запустить». Внешние процессы могут продолжать занимать GPU; worker сообщает реальную CUDA/OOM-ошибку и предлагает освободить память, не завершает сторонние процессы.

Отмена посылает SIGTERM только принадлежащей Studio группе worker, включая запущенный им FFmpeg. Через ограниченное время применяется SIGKILL той же группе. Сначала подтверждается завершение процесса, затем задача фиксируется как `cancelled`; чужой PID после перезапуска приложения не используется для сигналов.

Закрытие Studio включает worker в существующий `before-quit` shutdown: прекращает свою активную подготовку и дожидается ограниченного завершения перед выходом. Состояние задачи записывается перед запуском, при смене этапа и при завершении. При следующем открытии незавершённая задача предыдущего процесса становится `interrupted`, с действием «Повторить». Продолжение с произвольного промежуточного этапа и фоновая работа после выхода не поддерживаются.

Публикация может завершиться непосредственно перед аварийным выходом main. Восстановление сопоставляет запись задачи с конечным manifest: существующий валидный результат отмечается `completed`, повтор не создаётся автоматически. Восстановление не удаляет сомнительные файлы; их проблема показывается пользователю.

## Выбор и совместимость профилей

Выбор карточки задаёт сразу пару модели и avatarId; выбирать несочетаемые значения отдельно в обычной форме больше не нужно. Main самостоятельно получает модель из повторно проверенного каталога и не доверяет переданному renderer типу модели.

При остановленном профиле выбор сохраняет актуальные поля формы через существующий profile store. После перезапуска Studio открывает сохранённый аватар. При запущенном профиле используется действие «Остановить и выбрать»: оно закрывает текущую сессию и останавливает профиль перед сохранением новой пары. Правила записи MP4 и микрофона такие же, как для создания. Универсальное правило остановки не допускает подключения MuseTalk-аватара к серверу Wav2Lip и не оставляет модель сервера отличной от сохранённой.

Старые profiles.json совместимы: версия профиля остаётся 1, сохранённые model/avatarId распознаются без миграции. Если выбранный каталог исчез или перестал быть готовым, профиль сохраняется, но запуск получает ошибку с действием «Выбрать другого аватара». В пустой библиотеке Studio предлагает создание; исходное значение default ID не подменяется несуществующей карточкой.

Проверка готовности запуска использует тот же каталог/валидатор, что и библиотека, вместо существования одной папки. Это предотвращает запуск незавершённых результатов, а также проверяет соответствие выбранной модели.

## Границы модулей и IPC

Предлагаемые модули:

- `desktop/electron/avatar-library.mjs`: сканирование, проверка структуры, чтение/запись manifest, переименование, миниатюры и публикация рабочего результата.
- `desktop/electron/avatar-jobs.mjs`: состояния задач, отдельный worker, журнал, отмена и восстановление. Его зависимости spawn/kill/clock внедряются для тестов.
- `desktop/electron/avatar-prerequisites.mjs`: проверки подготовки, не зависящие от голоса, портов и «Бати».
- `desktop/renderer/avatar-library.mjs`: диалоги, карточки, форма и отображение событий через переданный bridge; основное управление разговором остаётся в `studio.mjs`.
- `scripts/prepare_desktop_avatar.py`: проверяемый протокол worker, нормализация медиа и адаптер генераторов. Общая проверка медиа/результатов может быть вынесена в небольшой Python-модуль, когда это помогает тестированию без импортов моделей.

`main.mjs` соединяет эти модули с profile store, shutdown и supervisor; preload предоставляет только перечисленные операции. Renderer не получает Node API, произвольное чтение файлов или возможность запуска команд.

Операции bridge: список по текущему checkout, выбор исходника, проверка создания, запуск, отмена по jobId, получение состояния, переименование по avatarId и выбор карточки. Подписка на события возвращает функцию отписки. Начальное состояние содержит библиотеку и последнюю задачу, поэтому переоткрытие диалога не теряет прогресс.

Основные аргументы операции создания: нормализуемые настройки root/Python из формы, токен исходника, имя, модель и допустимые параметры. Системный диалог main возвращает непрозрачный токен выбора и безопасные сведения для превью; абсолютный путь из свободного поля renderer не используется как разрешение на чтение. На повторе источник берётся из проверенной рабочей записи.

Источник и миниатюры возвращаются как ограниченные изображения через main, без открытия произвольных file:// URL и без воспроизведения пользовательского видео в привилегированном контексте. Выбор аватара принимает ID карточки и актуальную форму профиля, повторно проверяет готовность и сохраняет пару модели/ID. Все новые IPC используют существующий `trusted` sender check. Fixture-режим отключает реальную подготовку и инъецирует контролируемый worker и каталог во временных директориях.

## Проверки и критерии приёмки

Автоматические проверки без GPU:

1. Библиотека обнаруживает все три формата, правильный порядок кадров, старые каталоги и новые manifests; скрывает рабочие результаты; выдаёт причины неполных/противоречивых данных.
2. Кириллические и одинаковые имена, переименование, атомарная запись и ошибки записи не повреждают профиль или каталог. Удаление исходного пользовательского файла не влияет на опубликованный результат.
3. Пути и симлинки не выводят чтение, rename или cleanup за разрешённые корни. Коллизия ID не перезаписывает чужие данные.
4. Fake worker проверяет прогресс, malformed-события, exit без результата, ошибку, отмену, поздние события, тайм-аут shutdown и остановку только своей группы. Повтор после перезапуска не сигналит старому PID.
5. Проверки создания не требуют готового аватара, голоса, Qwen или базы, но находят отсутствующие веса подготовки и несовместимый вход.
6. Python-тесты с подменёнными генераторами проверяют нормализацию, числовое имя фото, пустое видео, отсутствие лица, соответствие артефактов и протокол завершения без загрузки моделей.
7. Smoke Electron с fixture показывает карточки, выбор, создание, прогресс, отмену, ошибку/повтор и сохранение библиотеки/выбора при повторном запуске. Проверяется остановка перед выбором и блокировка переключения во время подготовки.

При реализации выполняются `npm test`, `npm run build`, `npm run smoke` в `desktop`, а также соответствующие Python-тесты в окружении LiveTalking. Проверки существующего разговора, «Бати» и остановки должны продолжать проходить. Тесты баз используют только отдельные тестовые базы.

Практическая проверка с локальными весами и GPU: создать MuseTalk из фото и короткого видео, Wav2Lip из видео, выбрать каждый результат и подключить WebRTC; проверить озвучивание, перезапуск приложения и отмену подготовки. Проверка использует отдельные временные ID и не изменяет существующие аватары. Отчёт разделяет проверки с fixture и реальную генерацию; отсутствие практического запуска GPU не считается доказательством качества аватара.

Документация после реализации: обновить `desktop/README.md` — библиотека, требования подготовки, поддерживаемые входы, хранение/отмена и голос отдельно; убрать создание аватаров из перечня будущих работ. Актуализировать раздел Studio в `/home/kmrov/live/AGENTS.md`, не сохраняя там состояния процессов и секретов.

Успех означает: пользователь создаёт первого аватара из файла без ручных команд и готового старого аватара, после перезапуска видит созданные и старые карточки и выбирает их без ввода slug. Ошибка, отмена или закрытие не публикуют неполный результат и не завершают процессы, не принадлежащие Studio.
