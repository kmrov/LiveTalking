# LiveTalking desktop for Linux

Date: 2026-09-28

## Purpose and scope

Build a polished personal Linux desktop application for the LiveTalking setup in this repository. It should open a usable conversation workspace, start configured local LiveTalking, speech, and Batya services without terminal commands after initial setup, and make voice, avatar, brain, LLM, and WebRTC settings understandable. Another Linux user should be able to install the desktop application and complete a guided setup using their own Python environments and model weights. The application is not a bundle of Python, CUDA, databases, and model weights.

The first release supports both an in-app WebRTC preview and sending the avatar stream to Head in Jar or another WHIP receiver. It uses the existing LiveTalking engine and APIs. The desktop interface borrows the restrained dark visual language and clear workspace hierarchy of Head in Jar; it does not reuse Head in Jar's code or assets.

Windows and macOS support, model downloads, automatic installation of CUDA/Python packages, multi-user operation, and remote administration of LiveTalking are outside this first release. The setup assistant supplies actionable checks and instructions for missing dependencies. Batya is an optional brain mode; direct LLM chat remains available when Batya is not configured.

## Chosen approach

Create an Electron application in a new `desktop/` directory of this repository. The Electron main process owns local files, saved profiles, secret handling, process startup, health checks, and logs. A local renderer presents the UI and talks to the main process through a narrow preload API. The renderer uses LiveTalking's HTTP and WebRTC interfaces for sessions and media. Python inference stays in the existing server and separate model services.

The desktop application runs against an explicit compatible LiveTalking source directory. The setup assistant proposes the current checkout when available and lets other users select their own checkout. Linux packaging contains the Electron application and setup guidance, not Python environments or weights. The app checks the selected source version and required capabilities before starting it. A missing or incompatible checkout gets a specific fix instruction rather than a generic connection error.

Other approaches considered:

- Wrapping the existing web pages would ship sooner, but would keep setup, voice, avatar, and service status in separate pages with no coherent desktop workflow.
- Embedding or rewriting inference inside Electron would duplicate the Python engine and make model updates and GPU troubleshooting harder.

## First-run setup and profiles

The setup assistant collects a LiveTalking checkout, the LiveTalking Python executable, local ASR and TTS executables or external service URLs, and model locations. For Batya mode it also collects a Batya checkout, its separate Python 3.13 environment or `uv` executable, a PostgreSQL connection, and Yandex credentials. It checks that paths exist, that each selected Python can import its own required modules, that requested model files are available, that configured ports are free or occupied by compatible services, that PostgreSQL with pgvector is reachable, and that the selected local inference path sees a supported NVIDIA GPU. Every check shows its result and a concrete recovery step. It never silently installs packages or downloads weights.

The app offers a local Qwen voice profile based on the current `scripts/start_qwen_avatar.py` flow. It can reuse already running, compatible ASR/TTS services, and can be configured to use external ASR/TTS URLs. A simpler TTS backend remains selectable when supported by LiveTalking. Profiles store paths, backend choices, model identifiers, ports, voice, avatar, brain mode, nonsecret LLM settings, and WebRTC destinations. The last successful profile opens by default. On normal launch, the app starts that profile automatically; an explicit Stop control and an auto-start setting remain available.

The first release saves profiles under Electron's per-user application data directory. Voice references are copied to an app-owned `voices/` directory so moving the original WAV does not break a saved profile. Generated avatars and recordings remain in the selected LiveTalking data directory, with their paths shown in the UI. Profile export omits secrets and private voice audio unless the user explicitly exports those files separately.

## Local process lifecycle

The desktop main process starts one supervisor for a managed local profile. The supervisor uses the existing startup logic for Qwen ASR, Qwen TTS, and LiveTalking, extended to emit structured status events instead of requiring the UI to parse free-form log lines. The existing CLI remains usable. The process lifecycle is: validate configuration, start or adopt ASR, start or adopt TTS, optionally start or adopt Batya's PostgreSQL container and FastAPI service, start LiveTalking, poll readiness, then enable session controls. The UI shows each step and its log path. Batya's database uses its existing Docker Compose definition and persistent volume; the app starts the `db` service when Batya mode is selected and Docker is available. If that database was already running, the app adopts it without claiming ownership.

The app records which processes and containers it started. Stop and application quit terminate only those owned resources in reverse order, with a bounded graceful shutdown followed by a forced stop if needed. The PostgreSQL volume remains intact. Adopted services stay running. If LiveTalking, Batya, or a model process exits, the workspace changes to a failed state and offers a retry with the relevant log excerpt. A restart applies startup-only settings such as model, TTS backend, brain mode, direct LLM provider, and port. Changes that can be applied by making a new session, such as avatar ID and Qwen reference voice, reconnect only that session.

The app-managed LiveTalking server binds to `127.0.0.1` by default. This requires adding a configurable listen host to the Python server; existing command-line behavior outside the desktop profile stays compatible. The local management endpoints must not be exposed by the app to the LAN. The renderer cannot invoke arbitrary executables or pass unvalidated shell strings to the main process.

## Workspace and screen flow

The primary **Studio** screen uses a large central avatar preview, a compact library/profile area, and a conversation panel. The top bar shows the active profile and separate LiveTalking, ASR, TTS, and optional Batya/database states. The conversation panel has typed text, microphone start/stop, recognized text, echo/chat mode, interrupt, speaking state, and recording controls. In Batya mode it also selects or creates a persistent conversation and shows its history after reconnecting. The player shows connection and stream errors next to the video. It works at common laptop widths by collapsing secondary panels while keeping the player and conversation controls visible.

The **Voices** screen creates a Qwen3-TTS Base voice profile from a WAV sample and an exact transcript, tests a short sample phrase, and lets the user select the profile for a session. This is reference-based voice cloning, not model fine-tuning. The UI validates the file format and transcript before saving. Other TTS backends expose only controls they support; the OmniTTS voice-upload interface is not presented as a Qwen feature.

The **Avatars** screen selects a source video, model type, and relevant generation options. It submits an existing `/api/avatar/task`, polls task status, shows progress or the actual error, and lists ready avatars. A ready avatar can be selected for a new WebRTC session. The desktop will add a small avatar-listing endpoint or local manifest discovery so the user need not type avatar IDs. To avoid GPU contention, the first release stops the active preview session before starting generation and restores it when generation completes or fails.

The **Connections** screen manages the in-app WebRTC preview and outgoing WHIP destinations. The preview uses `/offer` and stores its session ID for conversation calls. Outgoing WHIP uses the existing `/api/whip/connect`, `/api/whip/status`, and `/api/whip/disconnect` controls with destination URL and optional bearer token. Head in Jar is a named destination preset; users paste its WHIP URL and token from Head in Jar. Preview and outgoing status are shown separately. A connection failure does not claim that LiveTalking itself has stopped.

The **Brain** screen chooses Batya or direct LLM chat. Batya mode shows conversations, saved memories, and text-document upload through Batya's API. It does not edit Batya's PostgreSQL data directly. The **Settings** screen edits service paths, model choices, Batya address and database setup, direct LLM provider, model name, prompt, and connection defaults. Direct LLM mode supports the current Yandex, DashScope, and OrcaRouter providers and one configurable OpenAI-compatible chat-completions endpoint. Supporting the configurable endpoint requires a focused LiveTalking backend addition. API keys are passed to the launched Batya or LiveTalking process through its environment, not command-line arguments or profile JSON. On Linux, keys are saved only through an available desktop secret service; otherwise they are held for the current app session and must be entered again after restart. The UI labels settings that require a server restart.

## Batya brain integration

Batya is a separate FastAPI service in `~/batya` with a Python 3.13 environment, PostgreSQL/pgvector storage, and Yandex AI Studio. It already exposes health, conversation, message, memory, and document endpoints. LiveTalking uses a new `batya` chat provider rather than sending Batya-mode text to its existing direct LLM providers. The Electron app and external LiveTalking clients can both send chat turns through LiveTalking's `/human` endpoint to this provider; echo mode still speaks text directly. The desktop creates or selects a Batya conversation through Batya's API and passes its ID in the WebRTC offer. If an external client supplies no ID, the adapter creates a conversation for that session and exposes the ID in session status so the client can resume it later. `/human` accepts an optional request ID; otherwise the adapter generates one and reuses it on network retry, matching Batya's idempotency contract.

The adapter consumes Batya's SSE events and forwards turn events to the existing LiveTalking `/sse` session stream. `delta` text may be shown provisionally in the desktop conversation view; `reset` clears that provisional text; `done` is the authoritative saved answer. Only the `done` text is queued to LiveTalking TTS, because Batya can reset earlier deltas after a tool call. `error` becomes a visible failed-turn event and does not enqueue speech. This prioritizes a correct spoken answer over lower first-audio latency. A later Batya protocol with committed speech chunks could allow safe incremental TTS without changing the desktop/LiveTalking boundary.

Turns for one Batya conversation run sequentially. Interrupt immediately clears avatar speech and suppresses audio for an older turn. The Batya request is allowed to reach a stored completion before the next turn starts, so the persistent history stays ordered. The app shows that the brain is still finishing a turn when speech has already stopped. The same Batya conversation remains selected when the WebRTC preview reconnects or the desktop app restarts.

## Data flow and failure handling

Electron controls processes and local files. LiveTalking serves conversation and avatar APIs. WebRTC media flows directly from LiveTalking to the renderer or the selected WHIP receiver. Chat mode calls either Batya through the new adapter or the selected direct LLM provider; Batya alone owns its persistent conversations and memory. The renderer never holds filesystem or process privileges beyond explicit preload operations. The main process validates selected paths and URLs and does not expose a generic command-execution IPC method.

The app distinguishes `not configured`, `checking`, `starting`, `ready`, `reconnecting`, and `failed` service states. It reports missing dependencies, unavailable ports, incorrect model IDs, insufficient GPU memory, invalid credentials, failed avatar tasks, unavailable PostgreSQL, Batya turn errors, and WebRTC negotiation failures with their actual source and a next action. Retry operations are idempotent: repeated Start clicks cannot spawn duplicate service trees or duplicate Batya turns. The app preserves a bounded diagnostic log and offers an export that redacts API keys, database credentials, and bearer tokens.

## Verification and release criteria

Automated checks cover profile validation and migration, supervisor ownership and shutdown, readiness and error transitions, secret redaction, Batya conversation/request ID propagation, SSE `delta`/`reset`/`done` handling, duplicate-turn prevention, API adapters, and IPC permissions. A Linux desktop smoke test uses test backends or fixtures to exercise first-run setup, startup states, session connection, and settings without loading large models.

Manual verification on the current Linux machine covers a cold start of the configured Qwen ASR/TTS, Batya/PostgreSQL, and LiveTalking services; an echo turn; a Batya chat turn that persists through reconnection and app restart; direct LLM fallback; microphone transcription; interrupt; a Qwen voice sample; avatar generation from a test video; in-app WebRTC playback; recording; and outgoing WHIP delivery to Head in Jar. A second Linux checkout with no prepared environment is used to check that the setup assistant identifies every missing prerequisite and explains how to resolve it. The release artifact is a Linux AppImage or `.deb` for the Electron UI, with versioned compatibility notes for the LiveTalking and Batya checkouts.

Work should be delivered in four reviewable increments: (1) desktop shell, setup, process lifecycle, and direct conversation; (2) Batya service lifecycle, persistent conversations, and brain adapter; (3) voices, avatars, LLM settings, and WHIP output; (4) onboarding polish, diagnostics, Linux packaging, and end-to-end verification. An increment is accepted only when its stated workflow works in the running desktop application, not just through a backend API call.
